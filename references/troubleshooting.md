# 常见问题与恢复

先保住可用网络，再定位失败的环节。每次只改一个变量，记录改前状态、实际结果和恢复动作。本文不自动执行命令、修改网络或联系外部客服。具体系统菜单以当前版本为准。

默认记录四种结论：已通过、未通过、未验证、不适用。日志/截图只保留必要错误类型；删除账号、IP、卡信息、节点链接、访问令牌及授权链接。没有证据时保留未知，不把旧案例的修复当作本机结论。

## 1. Karing 启动超时、一直转圈或连接失败

先区分“应用窗口打不开”“VPN/TUN 服务起不来”“服务已启动但节点请求超时”。三者不是同一个故障。网络恢复办法应预先保存在本机，不能只放在可能断开的聊天中。

| 动作 | 应该看到 | 未达到时 |
| --- | --- | --- |
| 1. 记录客户端/系统版本、错误原文的脱敏片段、最近一次改动，查看是否只有 Karing 异常 | 能判断启动、权限、节点或访问哪个环节失败 | 信息不足先观察应用和系统 VPN 状态，不马上重装、清缓存或换版本 |
| 2. 若已断网，停止继续切换；按预先保存的方案恢复上一次可用客户端/节点与路由设置 | 普通 HTTPS 页面和助手的新回复重新可用 | 若失败的 Karing 隧道仍占用路由，在系统 VPN 设置中只断开该失败连接，再恢复已知可用连接；不要同时启动多个接管整机的隧道 |
| 3. 网络稳定后检查系统要求的网络扩展/VPN 权限、Karing 是否重复运行、核心错误日志 | 权限已由客户确认，启动错误有具体类型 | 权限缺失按系统提示由客户处理；不要关掉整机安全机制或删除全部 VPN 配置 |
| 4. 核对当前选中节点、客户端的实际本机监听端口和服务器服务状态；通过原配置导出内容核对参数 | 服务与端口正常，导入参数一致 | 端口被占用、服务未启动、参数不符分别修复；不凭截图手抄密钥或把 SSH 端口当代理端口 |
| 5. 若本机代理入口可用、启用 TUN 才失败，记录当前 TUN 网络栈；在当前版本提供选项且已备妥恢复方式时，单独试另一网络栈 | 新 HTTPS 请求、实际出口及助手新回复同时正常 | 无改善恢复原值。Mac 的 `mixed → gvisor` 可作为已有经验的一项尝试，不是所有平台必改项或通用保证 |
| 6. 有具体兼容错误时查 [Karing 官方 FAQ](https://github.com/KaringX/karing-docu/blob/main/docs/faq.md) 与 [发布说明](https://github.com/KaringX/karing/releases)，比较客户端/服务端版本 | 找到与当前平台、版本、错误一致的依据 | 无依据不降级、重装或更换客户端；需调整时先备份，仅从官方来源取得软件 |
| 7. 修复后重新验证本机代理、整机路径、浏览器出口、手机相关路径及重开客户端后的使用 | 本次修改影响的路径确实恢复 | 旧 VPN 下能聊天只算恢复成功，不算新节点已通过 |

`reality verification failed` 要核对客户端与服务端的公钥、SNI、short ID、flow、系统时间、版本兼容性等实际参数。不得单凭这一条报错断言服务器被封、芯片不兼容或必须降级。正常连接不为“对齐教程”而改动。

## 2. 微信、普通网页和助手同时断网

| 动作 | 应该看到 | 未达到时 |
| --- | --- | --- |
| 1. 确认故障范围：微信仅消息失败还是全部业务失败，普通 HTTPS、DNS 与助手是否也受影响 | 能区分单一应用和整机故障 | 多个应用同时失败，先查系统路由、TUN、DNS、VPN 冲突，不先判断 Claude 账号异常 |
| 2. 按改前记录恢复最近一次网络变更，并用原先可用连接测试 | 普通网页恢复；客户可自行确认微信是否恢复 | 仍失败时继续核对本机网络、路由器和运营商连接；不连续叠加新规则 |
| 3. 若只有微信异常，查看客户端路由/排除项、应用权限、必要的 UDP 路径及本次新增限制 | 能指出具体路径差异 | 没有证据就不新增全局直连或禁止所有 UDP；恢复无效改动后再比较 |
| 4. 修复后由客户确认微信接收/连接状态，并验证新 HTTPS 请求 | 受影响业务恢复，原因或未确定点已记录 | 不替客户发送测试消息；无法核验的业务保留待确认 |

浏览器经独立 HTTP 端口能上网，不证明整机应用都走通。退出应用、结束窗口或看到 VPN 图标，也不能证明系统路由已恢复。

## 3. 看到 QUIC/UDP 超时，要不要全部禁掉

不要只因日志含 `QUIC` 或 `UDP` 就禁止整机相关协议。先确定该错误是否与用户可见故障发生在同一请求、同一时段。

| 动作 | 应该看到 | 未达到时 |
| --- | --- | --- |
| 1. 在受影响应用重现一个非敏感请求，核对同时段目标与错误，排除仅后台探测失败 | 日志与实际故障有对应关系 | 业务正常则不修改协议设置，只记录可观察到的错误 |
| 2. 检查代理客户端和服务器是否允许所需 UDP、路由是否进入预期出口；与正常 HTTPS 请求作对照 | 问题缩小到传输或规则环节 | 连基本 HTTPS 都失败时先查通用网络，不优先把 QUIC 当根因 |
| 3. 只有存在依据且客户同意时，在受影响应用做可恢复的单项协议对照测试，保存原值 | 同一操作出现可重复差异 | 无改善立即恢复；一次改善只能支持本环境的判断，不推导全网必须禁 QUIC |
| 4. 决定保留修复前，复查微信等常用业务和目标应用 | 修复没有破坏其他已用功能 | 出现新故障恢复原值并记录，不以牺牲整机网络来消除日志提示 |

若当前界面无对应选项，先查当前版本官方文档，不复制其他系统的隐藏参数或全局防火墙命令。

## 4. DNS、IPv6、WebRTC 检查不明确

| 动作 | 应该看到 | 未达到时 |
| --- | --- | --- |
| 1. 确认检测是在实际登录浏览器中完成；读取客户端 DNS 设置、浏览器安全 DNS/DoH 和系统解析设置 | 配置来源和测试环境明确 | 不用另一个浏览器的结果替代；读取权限不够或页未加载记“未验证” |
| 2. 将解析器与配置的预期路径比较；需要时在获准的本机日志/网络诊断中查看请求走向 | 有证据说明查询通过哪条路径 | 解析器 IP/城市与 VPS 不同并不自动说明泄露；仅见陌生解析器也不能判通过 |
| 3. 分别测试公网 IPv6、WebRTC 暴露的公网地址，并与客户实际基线比较 | 地址范围符合当前配置 | 未测到 IPv6 只写“本次未观察到 IPv6 出口”，不能写“系统 IPv6 已禁用”；发现意外公网出口则处理后重测 |
| 4. 将结论与证据范围写入进度/可选面板 | 已证实项目与未知项分开显示 | 不把未知自动改绿色，也不把异常地址保存成新基线来消除报警 |

第三方风险评分只作辅助；不同服务的分值不混算，更不能据此承诺账号安全。若关键查询路径仍不明，补检或明确保留未完成状态，不伪造网络验收。

## 5. 2FA 不通过，或页面出现“时间”字段

验证码、2FA 密钥、恢复码、短信码不是同一项。不要按字符长度或在“账号串”中的位置猜字段。优先使用客户已经配置的官方身份验证器；不要要求客户把长期密钥粘贴到陌生网页或聊天。

| 动作 | 应该看到 | 未达到时 |
| --- | --- | --- |
| 1. 先读当前登录页提示，确认要的是验证器动态码、短信码、设备确认还是恢复码 | 客户选到了该次挑战要求的方式 | 用错方式就返回选择本人可用方式；没有任何方式则走账号提供方官方恢复 |
| 2. 验证器未配置时，由客户在账号的官方安全设置中按说明配置，自己保存恢复资料 | 验证器条目与目标账号对应 | 缺少原始设置或恢复权限时暂停，不从卖家截图推断密钥 |
| 3. 如可信工具有“时间/时间戳”字段，先读字段说明，保留当前时间/自动取值；不要在该字段填密钥或验证码 | 工具以当前真实时间生成动态码 | 字段意义不明就改用已配置的官方验证器，不编造时间戳、时区或“固定正确时间” |
| 4. 核对设备真实日期时间正确，保留自动校时；等下一轮新码后由客户及时输入 | 新码被接受并进入下一步 | 连续失败暂停，核对条目和系统时间；不要把旧码反复提交或修改系统时间来碰码 |

Google Authenticator 7.0 起不再提供独立时间校正设置，而是使用操作系统时间；菜单变化时按当前应用核对。[Google Authenticator 官方说明](https://support.google.com/accounts/answer/1066447?hl=en)

## 6. OAuth 跳到 localhost、回调拒绝连接或授权过期

本节仅在客户使用需要浏览器授权的桌面/本地程序时适用；普通 Claude 网页登录不必人为添加本地回调。OAuth 原生应用可使用本机回环地址接收授权结果；`localhost` 指向打开该地址的那台设备。[OAuth 原生应用规范](https://www.rfc-editor.org/rfc/rfc8252)

| 动作 | 应该看到 | 未达到时 |
| --- | --- | --- |
| 1. 记录错误类型，确认授权由哪个程序、哪台机器发起，原程序是否仍在等待 | 发起方、浏览器和回调的设备关系明确 | 在另一台手机打开电脑的 localhost 回调无法代替电脑接收；回到发起设备 |
| 2. 授权页提示已过期、state 不匹配，或原程序已退出时，取消这次等待并从原程序重新发起一次新登录 | 获得本次新授权页，原程序持续等待 | 不刷新旧回调、不复用旧链接或授权码；不把完整 URL 放入进度 |
| 3. 在同一设备的合适浏览器完成新授权；检查本机回环地址是否被浏览器代理或本次新增规则错误转发/拦截 | 回调到原程序，程序显示登录成功 | 先核对其官方支持的回调方式；不得把 localhost 改为 VPS 地址、开放公网端口或关闭全部防火墙 |
| 4. 若程序官方提供手动回填码等替代方式，由客户按当前指引使用 | 原程序确认授权完成 | 没有官方替代入口时保留错误并查应用支持，不自造回填接口 |
| 5. 回到原应用发起一个非敏感请求 | 应用确实可用 | 浏览器显示授权成功但原应用仍等待，不算登录通过；继续排查本地接收环节 |

新授权链接可能含短期敏感参数，交由本人使用，不发送给外部人员。完成后只记录成功/错误类型，不保存授权码或令牌。

## 7. 卡号已有，CVV/CVC 还没有

卡号识别银行卡；有效期说明有效期限；CVV/CVC 是卡安全码，常见为三位或四位；短信/银行动态验证另有用途。它们不能互相替代。虚拟卡的安全码展示或交付方式以发卡方官方说明为准，不能从卡号计算或猜出。

| 动作 | 应该看到 | 未达到时 |
| --- | --- | --- |
| 1. 客户在发卡方官方 App/网页查看卡是否激活，核对其“卡详情/显示安全码”等真实入口 | 本人能够取得此次支付要求的完整卡资料 | 找不到入口、需审核或约定通知未收到时，付款前置仍为待处理 |
| 2. 若发卡方原说明要求收邮件/短信，由本人检查对应渠道和垃圾箱，再从官方 App/官网进入客服 | 发卡方说明资料获取方式、卡状态与预计处理安排 | 不向第三方“查 CVV”网站付费，不在聊天/工单正文直接附全卡资料 |
| 3. 向发卡方核实该卡是否支持目标币种、线上订阅、Google Pay 网页支付及相关验证 | 支持范围和限制得到明确答复 | 不支持就由客户选择其他本人合格方式；不要继续充值试运气 |
| 4. 资料齐全后回到原渠道重新核对订单并由客户付款 | 订单及权益有实际成功依据 | 资料齐全、绑卡成功分别记录；都不能提前算订阅完成 |

本版案例停在“CVV 未收到”；Google Pay 绑卡和最终付款仍待验证。保留已经可用的免费账号，不为补安全码重建网络或换 Claude 账号。

## 8. Google Pay 不出现、绑卡失败或付款被拒

| 动作 | 应该看到 | 未达到时 |
| --- | --- | --- |
| 1. 先辨明是网页 Google Pay、Google Wallet 添加卡，还是 Google Play 应用内购 | 渠道与当前失败步骤明确 | 只有 Google 登录页不算付款页；回到 [付款渠道表](accounts-payment.md#5-选择付款渠道) |
| 2. 没有 Google Pay 按钮时，查看该收银台实际接受的方式 | 客户能选已有合格渠道 | 不保证按钮一定出现；可结束此分支，不让客户反复改地区、换号或买礼品卡 |
| 3. 绑卡/付款失败时由本人核对卡状态、真实账单资料、验证消息及发卡行限制 | 错误被缩小到可处理环节 | 记录脱敏错误，与发卡方或 Google 官方支持核对；不通过反复提交碰运气 |
| 4. 如银行显示扣款，先查是预授权、待处理还是已结算，再查商户订单和 Claude 权益 | 资金状态与订单对应 | 暂停第二次购买；由客户提供官方所需凭据给相应官方渠道，不发到本教程仓库 |

Google Pay 官方帮助明确区分商户订单问题与发卡机构拒付；网页付款是否受理还取决于商户和可用支付方式。[Google Pay 网页付款与故障说明](https://support.google.com/googlepay/answer/7644068?hl=en)

## 9. Apple 无法完成购买、已扣款未到账

| 动作 | 应该看到 | 未达到时 |
| --- | --- | --- |
| 1. 客户核对 Apple 购买账号、Claude 目标账号、订单、金额和付款方式，查看有无待付款旧订单/当前购买限制 | 找到具体失败提示或订单状态 | 余额不足不代表应该无限充值；已扣款先查权益归属，不重新买 |
| 2. 卡被拒时核对真实账单资料，并向发卡方确认交易限制与验证要求 | 付款工具能满足当前交易条件 | 发卡机构才能解释其拒付原因；不靠更换代理解决所有支付拒绝 |
| 3. 当前页面提示 Purchase Not Completed 且提供 Continue/复核入口时，由客户按当页提交购买复核 | 获得提交状态或官方后续安排 | 没有该入口时从 [Apple 订阅与账单支持](https://support.apple.com/billing) 查对应问题；不假定始终有在线聊天或由助手代发 |
| 4. 官方要求等待时记录实际起点、时区、时长和下次动作，由客户保存案件资料 | 下一次处理时间明确 | 不把经验里的“两天”或“72 小时”写成官方统一期限；未获答复时不要编造解限时间 |
| 5. 订单已成功而 Claude 仍为免费时，核对原购买账号与 Claude 登录账号，按 App 当页可用的恢复购买/帮助入口处理 | 正确账号权益恢复 | 无恢复入口或仍不同步，客户联系官方并提供所需订单资料；不重复购买 |

Apple 当前提供具体拒付排查与购买复核流程，执行时重读 [官方说明](https://support.apple.com/en-gb/108095)。仅凭购买失败不能断言账号已永久受限。

## 10. 账号受限、服务故障、退款与取消

| 动作 | 应该看到 | 未达到时 |
| --- | --- | --- |
| 1. 先阅读当前错误并查 [Claude 服务状态](https://status.claude.com/)，区分服务中断、网络超时、登录验证和账号限制 | 故障类型有依据 | 不把一次超时称为封号，不凭 IP 分数推断账号结果 |
| 2. 账号页明确限制时，由客户从 [Claude 官方帮助中心](https://support.claude.com/) 查申诉/支持入口，说明本人真实情况 | 官方受理状态或下一步要求 | 不编造身份、地点、旅行或用途，不新建账号规避限制；指导人员只起草客户确认的事实 |
| 3. 涉及退款时先确定原订单渠道，阅读 [Claude 当前退款说明](https://support.claude.com/en/articles/12386328-request-a-refund-for-a-paid-claude-plan) | 明确向谁申请、应提供什么 | 不保证退款，也不把个别反馈写成 Google Pay 永不退款；Apple 收款找 Apple，其他渠道按当页官方指引 |
| 4. 不再需要续费时，由客户进入原渠道的 [取消流程](https://support.claude.com/en/articles/8325617-cancel-your-pro-or-max-subscription)，核对取消结果 | 显示到期/取消状态及剩余权益期 | 删除应用、退款申请或发出客服消息不自动等于取消成功 |

支持消息默认由客户本人提交。本说明不授权助手自动发送邮件、工单或客服消息。

## 11. 可选面板、防火墙或断线保护导致异常

这些功能默认不安装，不是免费登录或订阅交付的强制门槛。

| 动作 | 应该看到 | 未达到时 |
| --- | --- | --- |
| 1. 确认客户是否明确选择该功能，读取实际配置与改前备份 | 用途、范围与恢复入口明确 | 无需求就不继续加装；不存在的功能记“不适用” |
| 2. 面板显示全绿时检查每项依据：进程、端口、抽样出口、DNS、断线行为是否各自验证 | 只对确实测过的范围给结论 | 进程在线不证明请求成功；DNS/断线行为未知须显示未知，不能用整体绿色掩盖 |
| 3. 新防火墙/应用限制造成断网时，使用其预先准备的撤销方法只恢复本次规则 | 受影响业务恢复 | 不清空全部防火墙、不修改与任务无关的策略；无法确定规则归属时先查备份 |
| 4. 客户明确需要断线保护测试时，先安排本机恢复步骤和不会影响付款的时间，再分别验证节点失效与客户端退出 | 两种情形的真实行为各有记录 | 未测试只能写未验证；浏览器断网不能证明应用子进程与工具调用全部被阻断 |

恢复可用网络优先于继续增加限制。修复后重新确认客户原本要用的应用，不把“面板不报警”当最终目标。
